# Deployment — GKT + Find Your 7 Twins

## 1. Publish the GKT frontend

Keep the existing GKT repository as the GitHub Pages site. Copy the contents of `gkt/twins/` into a `twins/` directory in that repository.

The existing `gkt/index.html` is the actual current production page from the supplied repository, with only the Find Your 7 Twins entry points added (and the supplied favicon reference corrected to the favicon file that already exists in the repository).

Then:

```bash
git add index.html twins/
git commit -m "Integrate Find Your 7 Twins"
git push
```

Do not delete or replace the existing site files.

## 2. Deploy the FastAPI backend on Render

Render is used because GitHub Pages cannot execute FastAPI/Python server code. Render supports Docker services, managed PostgreSQL, environment variables, and persistent disks. The included `render.yaml` provisions the backend architecture.

From the Render dashboard, create a Blueprint from this repository/package and sync `render.yaml`.

The API service is configured for a paid `2c-4g` web instance because InsightFace model loading is not realistic on a 512 MB free instance. A persistent `/data` disk stores uploaded images and the downloaded InsightFace model cache. Render documents persistent disks as the mechanism for retaining service filesystem data across deploys/restarts.

## 3. Set SMTP secrets

In the Render service environment, set the four SMTP values:

```text
SMTP_HOST=...
SMTP_PORT=587
SMTP_USERNAME=...
SMTP_PASSWORD=...
SMTP_FROM=...
```

Do not commit these values.

## 4. Get the real backend URL

After the Render service deploys, copy its actual HTTPS URL from Render. Do not invent or guess it.

Open `gkt/twins/config.js` and set:

```javascript
window.TWINS_CONFIG = Object.freeze({
    API_BASE: "https://THE-ACTUAL-RENDER-URL"
});
```

Then commit and push `gkt/twins/config.js` to the GKT repository.

## 5. Migrate the existing SQLite database (optional)

The production ZIP intentionally does not ship the existing local database because it contains real user records and reset-token data.

If those existing records are meant to be preserved, first deploy the PostgreSQL database and then run:

```bash
export DATABASE_URL='postgresql://USER:PASSWORD@HOST:5432/DATABASE'
python backend/migrations/migrate_sqlite_to_postgres.py --sqlite /path/to/original/twins.db
```

Then copy the original `backend/uploads/` files to the persistent disk's `/data/uploads/` directory. The migration script preserves user IDs, swipes and password-reset-token rows.

Do not expose the SQLite database or `.secret_key` publicly.

## 6. Production environment

The Blueprint configures:

```text
ALLOWED_ORIGINS=https://gkt.com.np
FRONTEND_RESET_URL=https://gkt.com.np/twins/
STORAGE_DIR=/data
INSIGHTFACE_ROOT=/data/insightface
INSIGHTFACE_MODEL=buffalo_l
MAX_UPLOAD_BYTES=10485760
DEV_RESET_MODE=false
```

`JWT_SECRET_KEY` is generated by Render. Never replace it with a value committed to Git.

## 7. Password reset

For production, `DEV_RESET_MODE` must remain `false`. The backend only returns the development reset URL when development mode is explicitly enabled. The normal production flow sends the link through the configured SMTP provider.

The frontend keeps the existing explicit `submit` listener and `event.preventDefault()` reset flow. On successful reset it clears the token from the URL, leaves the success message visible, then returns the user to login. Errors remain visible.

## 8. Final URLs

```text
https://gkt.com.np/
https://gkt.com.np/twins/
```

The backend URL is the actual HTTPS Render URL you receive after deployment; it is not hard-coded in this package.

## 9. Test after deployment

1. Open the GKT homepage.
2. Open `/twins/`.
3. Register with one face in the uploaded image.
4. Confirm the visual similarity disclaimer.
5. Log out and log back in.
6. Use Forgot Password.
7. Confirm the email reset link opens `/twins/?reset_token=...`.
8. Change the password and verify the page does not reload.
9. Confirm the reset token disappears from the URL after success.
10. Upload/update a profile photo.
11. Turn discoverability off and confirm the profile is not returned as a public candidate.
12. Turn discoverability back on.
13. Test pass/like decisions and a mutual Twin Match.
14. Test account deletion and confirm the profile photo disappears.
15. Check `/health` on the backend.


## Free-tier deployment

If no paid Render resources are available, deploy the `backend` as a Free web service. The backend no longer loads InsightFace, so it fits the 512 MB Free runtime much better. Keep `JWT_SECRET_KEY` (or the existing `JWT_SECRET`) stable, `ALLOWED_ORIGINS=https://gkt.com.np`, and `FRONTEND_RESET_URL=https://gkt.com.np/twins/`.

Free Render storage is ephemeral, so local SQLite and uploaded photos may disappear after restarts, redeploys, or idle spin-down. Treat this as a demo/test deployment until durable database and object storage are added.
